# Piecewise 稀疏注意力：CPU 参考实现与可行性分析

这个目录是**上卡之前就能做完的那一半**：把补偿的代数写对、把误差界验掉、把"能稀疏到多少"算清楚。
全部内容纯 CPU 可跑（几秒）。

```bash
python test_sparse_attn.py                                  # 约 2 秒
python feasibility.py --synthetic --outdir results_feasibility
```

## 测试已经证明的四件事

```text
1. 稠密参考实现与 softmax(s)@v 一致（max rel err ~1e-7）
2. 一阶/二阶矩与逐元素暴力求和完全一致（代数没写错，可直接搬进 kernel）
3. 实测的 A 段相对误差始终不超过理论界 (Σ r_j ||v_j||)/||n_A||
   —— 推导文档的命题 1/2 在真实数值上成立
4. 单 key 的 break-even 点恰好在 |delta| = 1：
   此时一阶权重 1+delta = 0，一阶近似的相对误差 = 1 = 硬丢弃。
   |delta| < 1 时一阶更好，|delta| > 1 时一阶更差（会给出负权重）。
```

第 4 条是整个项目最重要的技术结论之一：**泰勒补偿不能无脑作用于被丢弃的全部 key**，
必须按 `delta` 分段（这就是 piecewise 的数学必要性，也是答辩时最容易被问的点）。

## 相图：补偿到底在什么区间有效

用 `feasibility.py --synthetic` 扫 logit 散布（k_scale 越小 = 注意力越平坦）得到的实测结果
（N=192, top-m 随稀疏率变化, tau=0.2）：

| logit std | 稀疏率 0.9 时的硬丢弃误差 | 一阶补偿误差 | 补偿收益 |
|---|---|---|---|
| 0.022 | 3.33 (333%) | **0.0013 (0.13%)** | **2561×** |
| 0.056 | 3.30 | 0.0089 (0.9%) | 373× |
| 0.112 | 3.25 | 0.041 (4.1%) | 79× |
| 0.225 | 3.12 | 0.34 (34%) | 9.2× |
| 0.393 | 2.88 | 2.15 | 1.3× |
| 0.674 | 2.40 | 2.38 | **1.0×（补偿失效）** |
| 1.12 | 1.55 | 1.55 | **1.0×（补偿失效）** |

结论：**补偿的收益随 logits 分散度快速衰减；std ≳ 0.35 之后 A 段几乎为空，补偿退化成硬丢弃。**
所以"PISA 能省多少"不是先验给定的，而是**必须先测出该层/该头的 logits 分布**才能回答的问题。

这一条同时解释了文献里互相矛盾的稀疏率结论：不同模型、不同层、不同头的 logits 分散度差异巨大，
在平坦头上有 3 个数量级的收益，在尖峰头上收益为 0。

## 一个更强的推论：精确预算不该花在最高 logit 上

一阶近似在 `delta = 0` 处是**精确**的（1+0 = e⁰），误差随 |delta| 单调递增。
也就是说，**注意力质量最大的那些 key 恰恰是补偿最准的地方**，把它们全部拿去精确计算是浪费。
`feasibility.py --compare` 在"两者精确 key 数完全相同"的前提下比较了两种分配：

```bash
python feasibility.py --synthetic --compare --outdir results_feasibility
```

| logit std | 精确 key 数 | 稀疏率 | top-m 精确（常规做法） | 中段精确（本推导） |
|---|---|---|---|---|
| 0.112 | 19 | 0.90 | **0.041** | 0.122 |
| 0.225 | 134 | 0.30 | 0.560 | **0.131** |
| 0.393 | 169 | 0.12 | 0.210 | **0.116** |
| 1.123 | 163 | 0.151 | **0.048** | 0.065（p90 退化到 0.34） |

在中间区间（std≈0.2–0.4，也正好是补偿唯一有效的区间）中段精确方案误差低 2–4 倍，
在极分散时反而更差。**这是一个可被真实数据证伪的设计选择**，也是本项目里最像"研究"的一块：
上卡后抓一次真实 logits，用 `--delta-file` 就能验证这个结论在你的模型上是否成立。

## 误差代理的标定（重要）

真实规模（N≈3e4）上算不出 `Σ r_j v_j` 的精确值，只能用只依赖 logits 的代理。
`feasibility.py --calibrate` 在合成分布上把两种代理与真实误差做了对照：

```text
bound_worst = rho_drop + Σ_A r_j w_j / z      （默认使用）
    补偿主导区间（rho_drop≈0）: 与真实误差的比值 0.71 ~ 1.24  -> ±30% 内，可直接用
    丢弃主导区间（rho_drop 大）: 比值 0.32 ~ 0.65            -> 低估 1.5~3 倍（偏乐观）
proxy_rms   = rho_drop + sqrt(Σ_A (r_j w_j)^2)/z
    实测低估约 10 倍 -> 不可用于判定（原因：v_j 的误差并非独立同分布，抵消远小于平方和假设）
```

所以：**补偿主导时代理可信；`delta_profile` 输出里的 `optimistic` 标志为 True 时，
说明该配置是丢弃主导、代理偏乐观，需要谨慎下结论。**

## 上卡后的替换路线

```text
1. 先用 hook 从 Wan2.1 抓真实 q/k/v（第 0/15/29 层、若干 head、若干采样步），
   导成 qkv.pt + delta.npy，然后：
       python feasibility.py --delta-file real_delta.npy --qkv-pt qkv.pt
   -> 得到"真实分布下能稀疏到多少"的答案，以及每层每头的补偿收益排序。

2. 把本文件的 masks（E/A/D）换成 block 级掩码：
       torch.nn.attention.flex_attention 的 block_sparse mask modifier
   （不要用"先算 N×N 再套 mask"的写法：480p 时单头 score 矩阵就 2.15GB，含 CFG 4.3GB）

3. 矩 M_A/S_A/G_A 在 kernel 里用流式累加实现（每个 block 一个 d×d/ d 向量），
   并在 query tile 内复用 —— 这是补偿"几乎免费"（(1+rho)d/(2N) ≈ 0.35%）的来源。
```
